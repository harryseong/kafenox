# Kafenox iOS

Photograph a coffee bag; the backend reads the label with Claude and files it
into your collection. The app is the client for the AWS backend in
[`../backend`](../backend).

## Running it

Requires **Xcode 26** (Swift 6.3, iOS 26 SDK). The project is generated by
[XcodeGen](https://github.com/yonaskolb/XcodeGen), so `Kafenox.xcodeproj` is
regenerated rather than hand-edited:

```bash
brew install xcodegen        # once
cd ios/Kafenox && xcodegen generate && open Kafenox.xcodeproj
```

The app needs an API Gateway key, which is **never committed**. Provision it
once into the Keychain (see `KeychainStore`); without it every request comes
back 403 and the collection loads empty.

```bash
aws apigateway get-api-keys --include-values \
  --query "items[?name=='kafenox-ios-dev'].value | [0]" --output text
```

To work on UI without a backend, flip `APIConfig.useMockData` to `true` — it
loads `Coffee.sampleData` and is compiled out of Release builds entirely.

## Module map

The Xcode target is deliberately thin — `@main`, `RootView` (the composition
root), and the tab shell. Everything else is a local Swift package under
`Packages/`, so the boundaries are enforced by the compiler instead of by
convention, and are reviewable as `Package.swift` rather than `.pbxproj`.

| Package | Contains | Depends on |
|---|---|---|
| `Core` | `Coffee` and its domain logic, `CoffeeRepository`, `AppConfiguration`, loggers | nothing (Foundation + OSLog) |
| `DesignSystem` | palette, typography, button styles, `FlowLayout`, `StatusBadgeView`, delete confirmation | `Core` |
| `Networking` | `APIClient` (a `CoffeeRepository`), `KeychainStore` | `Core` |
| `Features` | Catalog, Detail, Insights, Scan, Settings + their view models | `Core`, `DesignSystem`, `Networking` |

**Nothing depends on `Features`.** The five feature areas share one package
rather than one each, because they genuinely share state: Detail, Insights,
and the upload queue all read and mutate the same `CatalogViewModel`. Splitting
them further would mean hoisting that store into `Core` for no real gain at
this size — see [ADR 0002](docs/adr/0002-module-split.md).

`Core` and `Networking` are nonisolated by default (their values cross actor
boundaries); `DesignSystem` and `Features` use
`.defaultIsolation(MainActor.self)`, so UI code is main-actor without
annotation.

## Configuration

Build settings live in `Kafenox/Config/*.xcconfig`, not in the Xcode
inspector, so they diff readably. The API base URL flows
xcconfig → `Info.plist` → `AppConfiguration.current`; there is no URL literal
in source. Missing configuration crashes at launch on purpose — a
silently-wrong base URL costs far more to diagnose than a startup failure.

## Tests

```bash
swift test --package-path Packages/Core                    # fast, native
cd Packages/Features && xcodebuild test -scheme Features \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
```

Swift Testing throughout (`#expect`, `@Test(arguments:)`). Coverage is aimed at
state transitions and mapping — catalog filtering, upload-queue transitions,
insight aggregation, date parsing — not view bodies. `CoffeeRepository` is
faked by a hand-written actor stub rather than a mocking framework.

## Dependencies

None. Everything is URLSession, SwiftUI, MapKit, and UserNotifications.

## Accessibility

Most of the UI is custom, so the semantics are explicit rather than inherited —
see [ADR 0004](docs/adr/0004-accessibility-approach.md). None of it is covered
by the test suite, so after touching UI, check by hand:

```bash
# Type must resize live, without relaunching -- that's the whole point of
# .appFont being a @ScaledMetric modifier rather than a Font factory.
xcrun simctl ui booted content_size accessibility-extra-extra-extra-large
xcrun simctl ui booted content_size large            # back to default

# Reduce Motion: the scan screen's sweep and spinner should hold still.
xcrun simctl spawn booted defaults write com.apple.Accessibility ReduceMotionEnabled -bool true
```

With VoiceOver on, a catalog row must announce as a button, open on activation,
and offer Edit and Delete as actions; every field on the Edit screen must
announce its own name.

## Known gaps

- **Scan completion notifications are local, not push.** They fire while the
  app is alive (foreground, or the ~30s `beginBackgroundTask` window). If the
  app is terminated mid-extraction nothing fires; the coffee just shows as
  "New" on next launch. Real push would need APNs plus backend infrastructure.
- **No UI tests.** Critical flows (scan → queued, catalog → detail → verify)
  are only covered at the view-model level, and accessibility is verified by
  hand.
- **`list_coffees` scans DynamoDB.** Fine at a few hundred bags; revisit with
  GSIs past ~5-10k items.
- **Failed extractions have no retry.** Delete and rescan is the only path.

## On the committed API URL

`Config/Debug.xcconfig` contains a real API Gateway URL, and this repo is
public. That is deliberate and safe: the URL is not a credential. Every request
needs an `x-api-key` header whose value lives only in the Keychain and is never
committed, and the usage plan throttles at 50 rps / 100 burst, so the endpoint
cannot be used to read data or run up meaningful cost. A hard monthly quota
would be reasonable defense-in-depth if the endpoint ever gets attention.
